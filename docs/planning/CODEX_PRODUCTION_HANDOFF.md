## 2. 제품 목적

우리집식당은 가족 식사에서 반복되는 질문과 인원 조율을 줄이는 서비스다.

> 묻지 않아도 아는 집.

핵심 흐름은 다음과 같다.

`가입/로그인 → 가구 생성 또는 참여 → 식사 만들기 → 링크 공유 → 먹어요/안 먹어요 응답 → 인원 확정 → 기록 → 다시 만들기`

가족을 관리 대상으로 보이게 만들지 말고, 번갈아 식사를 제안하고 조율하는 관계를 유지한다.

## 3. 현재 구현 상태

현재 결과물은 정적 이미지 목업이 아니라 직접 조작할 수 있는 localStorage 기반 기능형 시제품이다.

기술 구성:

- Next.js App Router
- React와 TypeScript
- 전역 CSS
- localStorage
- Node 기본 테스트 러너

구현된 경로:

- `/`: 로그인 홈과 식사 없는 빈 상태
- `/tables`: 내 식탁
- `/calendar`: 식사 달력
- `/records`: 확정 식사 기록과 다시 만들기
- `/meals/new`: 식사 생성
- `/respond/[mealId]`: 비회원 응답, 제출 완료, 응답 수정

구현된 동작:

- 식사 생성과 화면 즉시 반영
- 먹어요/안 먹어요 응답 및 수정
- 참석, 불참, 미응답 집계
- 현재 인원으로 식사 확정
- 확정된 식사의 기록 표시
- 기록에서 새 식사 만들기
- 가구 선택 팝오버
- 알림 읽음 및 모두 읽음
- 전체 메뉴 드로어
- ESC, 바깥 클릭, 닫기 버튼으로 오버레이 닫기
- 데모 데이터 초기화
- 모바일 우선 및 데스크톱 중앙 레이아웃

현재 저장 키는 `our-home-restaurant-v1`이다.

## 6. 실서비스 목표 기술 구성

특별한 장애가 없다면 다음 구성을 사용한다.

- 애플리케이션: 기존 Next.js App Router 유지
- 데이터베이스: Supabase Postgres
- 인증: Supabase Auth
- 배포: Vercel
- 스타일: 기존 CSS와 디자인 토큰 유지

새 UI 라이브러리나 전역 상태 관리 라이브러리를 불필요하게 추가하지 않는다. 외부 프로젝트 생성, 계정 연결, 운영 배포가 필요할 때는 사용자 승인을 요청한다. 비밀키를 코드, 로그, Git에 기록하지 않는다.

## 7. 필수 실서비스 기능

### 인증

- 이메일 또는 매직 링크 로그인
- 로그아웃과 인증 세션 유지
- 최초 로그인 시 프로필 생성
- 보호 경로의 서버 측 인증 검사
- 비회원 응답 경로는 로그인 없이 접근 허용

### 가구

- 가구 생성과 초대 링크 또는 코드 참여
- 여러 가구 사이 전환
- 가족 구성원 목록
- `owner`, `co-admin`, `member` 역할
- owner만 가구 삭제와 owner 위임 가능
- owner와 co-admin은 구성원과 가구 설정 관리 가능
- UI뿐 아니라 서버와 DB에서도 권한 검사

### 식사

- 식사 생성, 조회, 수정, 취소
- 날짜, 시간, 종류, 메뉴, 메모, 생성자, 참여 대상 저장
- `open`, `confirmed`, 필요 시 `cancelled` 상태
- 실제 현재 날짜를 기준으로 오늘, 예정, 지난 식사 구분
- 식사 생성 결과를 홈, 내 식탁, 달력에 반영
- 기록에서 과거 식사를 복제해 새 식사 생성

### 응답

- 회원과 비회원 응답
- 먹어요/안 먹어요와 도착 시간
- 기존 응답 수정
- 참석, 불참, 미응답 집계
- 추측하기 어려운 공유 토큰
- 공유 토큰 폐기 또는 재발급
- 비회원은 사용자 계정 없이 이름만으로 존재 가능
- 비회원에게 식사 생성, 수정, 확정 권한을 부여하지 않음
- 동일 응답자의 중복 활성 응답 방지

### 알림

이번 단계에서는 앱 내부 알림만 구현한다.

- 식사 생성, 응답 변경, 미응답 등 핵심 이벤트 저장
- 읽음과 읽지 않음
- 모두 읽음

푸시, 문자, 카카오톡 자동 발송은 제외한다.

## 8. 최소 데이터 모델

- `profiles`
- `households`
- `household_members`
- `meals`
- `meal_participants`
- `meal_responses`
- `meal_share_links`
- `menu_requests`
- `notifications`

필수 규칙:

- 모든 운영 데이터는 가구 단위로 격리한다.
- `household_members.role`은 `owner | co-admin | member`다.
- 회원 구성원은 사용자 계정과 연결할 수 있다.
- 비회원 손님은 사용자 계정 없이 이름만으로 존재할 수 있다.
- 같은 식사에 동일 응답자의 활성 응답이 중복되지 않게 한다.
- 생성일, 수정일, 생성자와 필요한 외래키, 고유 제약, 인덱스를 둔다.
- 날짜와 시간대 저장 정책을 명시한다.
- Supabase Row Level Security를 활성화하고 정책을 마이그레이션으로 관리한다.
- 서비스 역할 키를 브라우저에 노출하지 않는다.

## 9. localStorage 전환

현재 localStorage에는 다음 정보가 있다.

- 현재 프로필과 가구
- 가구와 구성원
- 구성원 역할
- 식사
- 응답과 비회원 여부
- 메뉴 요청
- 알림과 읽음 상태

운영 버전에서는 이것을 신뢰 가능한 데이터 원본으로 사용하지 않는다. 서버 데이터로 교체하고, 기존 브라우저 데이터는 일회성 가져오기 또는 명시적인 삭제 안내를 제공한다. 데모 데이터 초기화 기능은 개발 환경에서만 제공하거나 운영 UI에서 제거한다.

## 10. 보안 요구사항

- 모든 입력을 서버 경계에서 검증한다.
- 클라이언트가 보낸 사용자 역할과 가구 ID를 신뢰하지 않는다.
- 가구 간 데이터 노출을 차단한다.
- 공유 링크 토큰의 원문 저장을 피할 수 있는지 검토한다.
- 공유 응답에 기본적인 요청 제한과 만료 정책을 적용한다.
- 비밀키 이름만 `.env.example`에 기록한다.
- `.env.local`과 실제 키를 커밋하지 않는다.
- 오류 응답에 내부 정보나 비밀키를 노출하지 않는다.
- 삭제 기능에 확인 절차와 참조 데이터 처리 정책을 둔다.

- 비회원 응답 화면에 로그인 사용자용 내비게이션을 표시하지 않음
- 로딩, 오류, 빈 상태, 제출 중, 중복 제출 상태 구현
